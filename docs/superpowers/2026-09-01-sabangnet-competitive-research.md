# 사방넷 경쟁 분석 — KidItem 상품등록 확장 판단 보고서

**작성일** 2026-09-01 · **대상** KidItem 제품 담당자 · **목적** 27개 몰 상품등록 확장 설계의 기준선 확보

## 1. 사방넷이 실제로 하는 일

사방넷은 "쇼핑몰 연동 기능 모음"이 아니라 **4개 계층으로 쪼갠 데이터 파이프라인**이다. 이 구조를 이해하지 못하면 왜 사방넷 세팅에 30일이 걸리는지 설명되지 않는다.

### 1.1 마스터 + 몰별 오버레이 2층 구조

사방넷은 상품 하나를 **품번코드(6자리 고유코드, 수정·중복 발급 불가)** 로 잡고, 그 아래 **단품코드(4자리)** 로 옵션을 건다. 이게 마스터다.

그런데 이 마스터의 상당수 필드는 **몰로 전송되지 않는다.** 공식 FAQ 원문: "사방넷 상품(품번) 내 배송비, 배송구분은 사방넷 내부 관리용으로 등록하는 정보이며, 쇼핑몰에 연동되지 않습니다." 마이카테고리·상품구분도 마찬가지다([출처](https://docs.sabangnet.co.kr:1975/r/viewer/content/sabangnet/22ef084ce42a59d5)).

몰에 실제로 반영되는 것은 **오버레이 계층**이다:

| 오버레이 | 담는 것 | 단위 | 등록 방식 |
|---|---|---|---|
| **쇼핑몰부가정보** (필수) | 출고지/반품지, 배송정책, 배송비 | 몰 × 쇼핑몰ID × 배송정책조합 | 건별 폼 (**대량등록 불가, 삭제 불가**) |
| 쇼핑몰부가정보Ⅱ | 배송정보 (11번가·스토어팜·ESM·인터파크·GS shop 전용) | 몰별 | 건별 폼 |
| 쇼핑몰카테고리 (선택) | 몰 카테고리 코드 | 몰 × ID | 몰 SCM 실시간 조회 후 선택 |
| 쇼핑몰별 별도정보 | 상품명·홍보문구·인증정보·판매가·원가·정보고시·상세설명 | 몰별 | 건별 팝업 **또는** 몰별 엑셀 대량등록/수정 |

> **교차검증 정정 1** — 원 리서치는 "부가정보와 카테고리를 몰별로 반드시 만들어야 전송 가능"이라고 했으나, **카테고리는 필수가 아니다.** 공식 매뉴얼 원문: "📌 쇼핑몰 카테고리코드는 필수항목이 아닙니다." 송신 팝업에도 "부가정보, 카테고리**(선택)** 코드를 선택합니다"로 되어 있다. 필수는 부가정보뿐이다([출처](https://docs.sabangnet.co.kr:1975/r/viewer/content/sabangnet/308bad98b0f7c520)).
>
> **교차검증 정정 2 (부담은 오히려 더 큼)** — 부가정보는 '몰당 1개'가 아니다. "💡 쇼핑몰 ID 별로 등록을 진행합니다"이고, 여기에 출고지·배송정책 조합이 곱해진다(실무 노트 예시 코드명: `jogilsang/당일발송/유료2500원/기본출하지`). 게다가 "📌 부가정보는 대량 등록이 불가하며 (…) 삭제가 불가하며, 사용하지 않는 부가정보는 사용여부를 '미사용' 처리합니다." **즉 (몰 수 × 계정 수 × 배송정책 수)만큼 손으로 만들고, 잘못 만들면 지울 수 없다.** 이것이 세팅 대행 시장의 진짜 원인이다.

> **교차검증 정정 3** — "쇼핑몰별 별도정보는 엑셀 대량등록만 지원"은 **틀렸다.** 공식 활용매뉴얼(2023.01)은 STEP1 건별 등록([상품관리 > 사방넷상품조회수정] 안의 `[쇼핑몰별 상품명등록]` `[쇼핑몰별 판매가등록]` `[쇼핑몰별 상세설명등록]` `[쇼핑몰별 속성설정]` 팝업)과 STEP2 대량 등록을 명확히 나눈다. 대량수정도 지원한다. 또 부가정보Ⅱ는 상품명/판매가가 아니라 **배송정보 전용**이다.

### 1.2 전송 계층 — 등록 / 수정 / 상태 / 재고가 전부 다른 메뉴

사방넷의 송신은 하나의 "publish" 액션이 아니라 **최소 5개 메뉴로 쪼개져 있다**:

- `쇼핑몰상품등록` — 신규 등록 (즉시송신 / 예약송신저장)
- `쇼핑몰상품등록(실패)` — 실패 전용 큐, `[실패상품등록송신]`으로 재전송
- `쇼핑몰상품수정` — 일반항목 / 상품상태 / 옵션재고 3분기
- `쇼핑몰상품품절` — 일시중지송신 / 완전품절송신
- `쇼핑몰옵션송신` — 옵션정보송신

**전송 단위는 "상품 N개 × 쇼핑몰 1개 × 쇼핑몰ID 1개 + 부가정보/카테고리 1세트"다.** 다몰 동시 전송이 없다. 공식 FAQ 원문 그대로: "① 상품 검색 후 체크 ② 쇼핑몰 선택 후 [상품등록송신] ③ [예약송신저장] ④ **쇼핑몰별로 1~3 작업 반복** ⑤ [쇼핑몰예약등록관리] 이동 ⑥ 저장된 작업 선택 후 [상품등록송신]"([출처](https://docs.sabangnet.co.kr:1975/r/viewer/content/sabangnet/51c43faea577b7a9)). 동시성은 '준비'가 아니라 '실행' 단계에서만 생긴다.

> **교차검증 정정 4** — 수정송신이 "매번 수동 트리거"라는 서술은 과장이다. `[쇼핑몰관리 > 스케줄러]`가 있고 "사방넷에서 수정한 상품 정보, 옵션 재고, 상태를 쇼핑몰에 전송할 수 있습니다"로 명시돼 있다. 다만 스케줄러는 **유료 부가서비스**이고, 자동화서비스Ⅰ·Ⅱ와 **병행 불가**다. 그리고 '수정함/수정안함' 라디오는 **일반항목 경로에만** 있다(7개 항목: 상품명·판매가·카테고리·수수료·이미지·상세설명·유료및부가서비스).

### 1.3 매핑 계층 — 코드 매핑 + 문자열 매핑

- **품번매핑**: 사방넷 품번코드 ↔ 쇼핑몰상품코드. **1:1만 허용.** "하나의 쇼핑몰 상품코드에 다수의 품번코드 매핑은 불가." 대량 매핑 엑셀도 몰별로 쪼개서 각각 업로드.
- **단품매핑**: 사방넷 단품코드 ↔ 쇼핑몰 옵션명. **문자열 비교 방식.** 대행사 주의사항 원문: "옵션 매핑은 문자열로 진행되기 때문에, 문자열 정보가 불규칙한 쇼핑몰은 불가하며, 작업 이후 쇼핑몰 옵션명을 변경하실 경우에는 매핑을 다시 진행하셔야 합니다"([출처](https://healsum.cafe24.com/product/%EC%82%AC%EB%B0%A9%EB%84%B7-%EC%83%81%ED%92%88%EA%B4%80%EB%A6%AC-%EB%B0%8F-%EC%A3%BC%EB%AC%B8%EA%B4%80%EB%A6%AC-%EB%A7%A4%ED%95%91-%EC%85%8B%ED%8C%85/11596/)).
- **표준카테고리**: 유일한 마스터-투-멀티몰 카테고리 자동화 장치. 지원 몰 14개.
- **쇼핑몰 옵션/속성관리**: 몰별 문자열 치환 사전(사방넷 "블랙:F" → 몰 "BLACK:FREE"). 1,500Byte 상한, 부분 일치 미적용.

### 1.4 동기화 루프 — 배치, 실시간 아님

- 스케줄러: **상품 10분 / 주문 30분** 단위. **00:00~06:00 미실행.**
- 상품 송신 대상은 "**상품 수정일 당일**"만. 어제 수정분은 자동 재송신 안 됨.
- 3PL 관측 실측: 주문수집 30분(최대 1시간), 클레임 10분(최대 20분), 송장 자동등록 매시 20·50분·**08:20~21:50만**([품고](https://guide.poomgo.com/2c58aea0-7620-8027-ae86-cf34d06ea5d6), [파스토](https://blog.fassto.ai/9e632037-b8bb-4d9a-986c-fe75a0cb5e46)).
- 재고 차감 시점은 송장 송신이 아니라 **출고 확정**. 그것도 재고관리 사용여부=사용함 + 품번/단품 매핑 완료 두 조건이 다 맞아야.

### 1.5 실행 계층 — 브라우저만으로 안 된다

"쇼핑몰에 상품을 등록하거나 주문 수집을 하기 전 설치해야 하는 프로그램 → **사방넷 클라이언트**"이고, 팝업 차단 해제가 필요하다. 카테고리 조회도 API 사전 동기화가 아니라 "사방넷에 세팅한 쇼핑몰의 로그인 계정으로 쇼핑몰 SCM에서 조회"하는 실시간 방식이다. **즉 사방넷 역시 상당 부분이 계정 로그인 기반 화면 연동이며, 순수 공식 API 제품이 아니다.** KidItem의 확장 화면 자동화가 "열등한 방식"이 아니라는 뜻이다.

## 2. 숫자로 본 사방넷

### 2.1 연동 몰 수 — 696이 실측, 650은 하드코딩

| 출처 | 숫자 | 성격 |
|---|---|---|
| 라이브 API `/hp-prod/features/count-malls` (2026-09-01 직접 조회) | **696** | 실측 |
| 사방넷 프론트엔드 번들 `app.js` 상수 `l="650"` | 650 | **마케팅 하드코딩** |
| 카페24 앱스토어 사방넷 앱 설명 | 600 | 갱신 지연 |
| WISA 2023 공지 | 약 450 | 시점 차 |
| [다우IDC 소개 페이지](https://www.daouidc.com/biz/sabangnet.do) | 200여 개 | **레거시 방치** |

**696개 내역**(2026-09-01 실측): 오픈마켓 68 / 소셜 7 / 종합몰 183 / 전문몰 338 / 홈쇼핑 19 / 복지몰 55 / 해외 26.
※ 표준카테고리 검증 세션의 별도 집계는 합계 696으로 같으나 분포가 다르게 나왔다(전문몰 340 / 종합몰 186 / 오픈마켓 89 …). 조회 시점 또는 분류 파라미터 차이로 보이며, **어느 쪽이 맞는지 확인 안 됨**. 합계 696만 신뢰할 것.

**중요: 696 중 실제 활성은 361개다.** 7개 기능 컬럼이 전부 `-`인 335건은 레거시 엔트리다(옥션↔ESM옥션, 11번가(구)↔11번가, 티몬↔티몬(신), **키즈노트↔키즈노트(신)** 식의 구/신 쌍). 활성 361개 분포: 오픈마켓 51 / 종합몰 96 / 전문몰 165 / 복지몰 37 / 홈쇼핑 11 / 소셜 1. `-`의 공식 정의는 사방넷이 밝히지 않았으므로 이 335건 해석은 **추론**이다.

**기능별 지원 수(696 전체 기준)**: 주문수집 O 343 / 상품등록 O 332 / 송장전송 O 327 / 문의수집 O 234·X 116. 활성 361 기준 품절처리 O 330 / X 17 / 개발중 14.

**"연동됨 ≠ 풀기능"**: 네이버페이(신)는 상품등록·수정·품절이 전부 X(주문수집·송장은 O). GS25는 반대로 상품 쪽만 O이고 주문·송장·교환·문의가 전부 X.

**개발중 13개** 공개(대림디움몰(신), 핏펫몰, 이녹, 해브어, 리비, ARA, 인천e몰, 사장이지 쇼핑, 감동타임, 도넛츠, Qoo10 Japan(MOVE), 비그룸, 네이트온). Amazon도 7개 기능 전부 '개발중'.

### 2.2 KidItem 채널과의 대조 — 여기가 결정적이다

696건 전수 검색 결과:

| KidItem 채널 | 사방넷 상태 |
|---|---|
| 온채널 / 꼬망세 / 키드키즈 / 보리보리 | **목록에 아예 없음** |
| 아이스크림복지몰 / 키즈노트(구) | 7개 기능 전부 `-` (레거시) |
| 키즈노트(신) | 전부 O |
| 도매꾹 / 티처몰 / GS shop / 롯데온 | 전부 O |
| 올웨이즈 / 토스쇼핑 | 문의수집만 X |

**"유아/완구/문구/교구/어린이" 키워드로 매칭되는 몰명이 사실상 없다.** KidItem이 이미 파이프라인을 만든 유아·교육 폐쇄몰 6개가 사방넷 커버리지 밖이다. 이건 우연이 아니라 사방넷의 신규 몰 편입이 **셀프서비스가 아니라 제휴·연동개발 협의**(biz_sb@daou.co.kr, 건별)로만 이뤄지기 때문이다. 몰이 작으면 사방넷이 붙일 유인이 없다.

### 2.3 가격 — 공식 API 실측값 (2026-09-01)

**본품 (월 사용료 + 1회성 가입비, VAT 별도)**

| 등급 | 월 | 가입비 | 월주문 | 상품DB | 몰ID |
|---|---|---|---|---|---|
| 싱글 | 150,000 | 100,000 | 2,000 | 700 | 8 |
| 레귤러 | 250,000 | 300,000 | 3,000 | 1,000 | 20 |
| 브론즈 | 300,000 | 500,000 | 10,000 | 3,000 | 50 |
| 실버 | 420,000 | 500,000 | 20,000 | 10,000 | 70 |
| 골드 | 520,000 | 700,000 | 30,000 | 20,000 | 100 |
| 스페셜1~4 | 750,000~1,450,000 | 1,000,000 | 50,000~ | 40,000~ | 무제한 |
| 플래티넘1~2 | 1,850,000 / 2,350,000 | 1,000,000 | ~350,000 | ~300,000 | 무제한 |

**상품 송신 수는 전 등급 무제한.** 과금 축은 주문 수·상품 DB 수·ID 수다. 약정 할인: 6개월 5%, 12개월 10%, 24개월 30%.

**부가서비스(별도 과금)**: 스케줄러 월 3만(싱글·레귤러·브론즈) / 5만(실버 이상). API 3.0 월 5만~50만. 알림톡 8원/건. 챗봇 월 9,900~650,000원. 사용자ID 추가 5,000원/월, 이미지호스팅 1GB 추가 10,000원/월.

**즉 월 15만원 싱글로 시작해도 자동수집을 켜면 18만원, 외부 시스템 연동까지 하면 23만원부터다.**

> **주의 — 리셀러 페이지와 불일치**: [다우IDC 페이지](https://www.daouidc.com/biz/sabangnet.do)는 "시스템 버전 + 연동 버전을 각각 필수 구매"하는 이중 구조(Basic/Standard/VIP + Level1~5)로 되어 있고 상품명·몰 수 표기가 현행 공식과 다르다. 리서치 초기에 인용된 "연동버전 Level1~5, 상품등록 2,000~100,000건 쿼터"는 **이 레거시 페이지 기준**이며, 현행 공식 요금 API에는 상품송신 무제한(-1)으로 나온다. **현행 계약 조건은 공식 견적 기준으로 봐야 한다.**

**사방넷 미니**: Starter1 무료 / Starter2 3,000원 / Starter3 9,000원, 가입비 없음. 단 자동화 부가서비스가 주문 3만~5만, 상품 5만~10만이고 **무료 티어는 자동화 구매 자체가 불가**. 풀필먼트 연동도 불가. 전형적 유료 전환 퍼널.

## 3. 사방넷이 못 하는 것 / 사용자 불만

**이 절이 KidItem 제품 결정의 핵심이다.** 불만을 "UI가 낡았다" 수준으로 요약하면 안 된다. 구조적 결함 7종으로 분류한다.

### 3.1 전송 결과를 믿을 수 없다 (가장 치명적)

세 가지가 겹친다.

1. **큐 상태가 거짓말한다.** 공식 매뉴얼 원문: "📌 상품등록송신시 **실제 등록 성공 여부와 상관없이 '처리완료'로 변경됩니다.**" 예약등록관리 화면의 '처리완료'는 아무것도 보장하지 않는다.
2. **유령 실패가 공식적으로 존재한다.** "[GS Shop], [패션플러스]와 같은 특정 쇼핑몰의 경우, 쇼핑몰 SCM 속도가 느려서 쇼핑몰에는 상품이 등록이 되었지만 발급된 쇼핑몰 상품코드를 조회하지 못해 사방넷에는 실패되는 경우가 발생합니다. (…) **온라인 문의로 상품코드 매칭을 요청합니다.**" — 즉 복구 수단이 고객센터 티켓이다([출처](https://docs.sabangnet.co.kr:1975/r/viewer/content/sabangnet/51c43faea577b7a9)).
3. **재전송이 멱등하지 않다.** "📌 같은 상품을 여러 번 재송신하는 경우 **상품이 중복으로 등록될 수 있습니다.**" 실패인지 확신할 수 없는 상태에서 재시도하면 몰에 중복 상품이 생긴다.

여기에 수정 전송 쪽 조용한 사고까지 붙는다: "💡 수정 전송 중에 팝업 창을 닫거나 클라이언트 오류로 인해 전송이 중단된 경우 **실패로 확인되지 않으며**, 마지막으로 전송 시도한 상품명과 판매가가 화면에 저장됩니다."

**판단: 사방넷의 전송 계층은 관측 가능성(observability)이 없다.** 이건 UI 개선으로 못 고치는, 아키텍처 수준의 부채다. KidItem의 최대 공격 지점.

### 3.2 예약 큐가 스냅샷이라 조용히 낡는다

"📌 [예약송신저장] 후, 상품명, 판매가, 브랜드 등의 정보를 변경한 경우, **이미 저장된 예약 작업 내역에는 변경한 내용이 적용되지 않으므로 주의합니다.**" 폐기는 '처리대기' 상태일 때만 가능하고 '처리완료'면 불가.

27개 몰에 밀어넣으려고 몰별로 26번 예약 저장을 하는 사이 상품을 고치면, 앞쪽 큐는 옛날 데이터를 보낸다. 그리고 3.1에 따라 그 사실을 알 방법이 없다.

### 3.3 되돌릴 수 없는 파괴적 동작이 경고 없이 있다

- **완전품절 = 영구 삭제**: "💡 상품의 영구 삭제기능이 있는 **ESM옥션, ESM지마켓, 11번가, 인터파크, 고도몰**의 경우 사방넷 [완전품절] 상태로 전송 시에 쇼핑몰에서 영구삭제 됩니다."
- **연동 내역 삭제 불가역**: "삭제한 내역은 복구가 불가", 그리고 "📌 **특정쇼핑몰은 사방넷에서 등록송신한 이력을 삭제한 경우 재연동 되지 않으므로** 반드시 [쇼핑몰 특이사항] 버튼을 클릭하여 확인합니다."
- **API OPT_TYPE 함정**: "한번 9로 선택된 상품은 다른 값선택이 불가능합니다" — 옵션 전체 삭제 후 재구성(2)을 쓰면 옵션코드가 사라져 재고관리가 붕괴하고, 안전값(9)으로 한 번 바꾸면 되돌릴 수 없다.
- 부가정보 삭제 불가(미사용 처리만), 매핑문자열 삭제 복구 불가, 전체 재고 초기화는 사방넷만 가능·복구 불가.

**판단: 위험한 동작에 confirm 게이트도, dry-run도, 되돌리기도 없다.** KidItem은 몰별 송장 등록에서 이미 "파괴적 → 검증 후 라이브" 원칙을 갖고 있는데, 이 원칙을 상품등록에도 그대로 적용하면 그 자체가 차별점이 된다.

### 3.4 세팅이 곱셈으로 커지고, 자동화가 안 된다

- 부가정보: (몰 × 쇼핑몰ID × 배송정책조합) 개수만큼 손으로 생성, **대량등록 불가, 삭제 불가**.
- 품번 매핑 대량등록: "여러 쇼핑몰을 한 번에 등록할 수 없습니다. **엑셀파일을 쇼핑몰별로 작성하여 각각 등록**해야합니다."
- 쇼핑몰별 별도정보: "단, **쇼핑몰별로 업로드합니다.**"
- 정보고시 템플릿: 최대 100개, **엑셀 대량등록/수정 시 적용 불가, 건별만.**
- 마이카테고리 매핑: "매핑 시 **최종 하위분류에서** 설정합니다" — 건별.
- 매칭카테고리: "건 별 수정만 가능하며, **대량 수정은 불가**."

**결과가 시장가격으로 나타난다.** 운영사 스스로 셀프 세팅 30일이라 했고, 대행 견적 단위가 "몰 10개 × 상품 150개 = 30만원"이다.

### 3.5 2패스 구조 — 등록만으로는 완성되지 않는다

신규등록 화면에서 못 하는 것: **3단 옵션**, **모음전/세트Ⅱ 연결**. 둘 다 "상품 등록 후 [사방넷상품조회수정]"에서만 가능(세트/모음전은 [사방넷단품대량수정]도 가능).

> **교차검증 정정 5** — 원 리서치는 "속성정보(상품정보고시)도 신규등록 불가"라고 했으나 **현행 기준 틀렸다.** FAQ에는 아직 "신규등록 시 설정이 불가"라는 낡은 문장이 남아 있지만, 같은 사이트의 매뉴얼(2026-08-31 갱신)에는 "**사방넷상품신규등록 메뉴에서 [속성등록&수정] 버튼 클릭**" 절차가 있고, 사방넷 배포 PDF(2024.01)의 신규등록 화면 캡처에도 해당 버튼이 보인다. **사방넷 공식 문서끼리 모순 상태다.**
>
> **교차검증 정정 6** — "속성정보 미등록이면 등록하자마자 전송 실패"도 과대해석. 원문은 "전송이 실패**될 수 있습니다**"(조건부)이고, 정보고시 필수 여부는 몰 정책에 따라 다르다.

> **교차검증 정정 7** — 신규등록 화면 입력 블록은 8개가 아니라 **11개**다: 기본정보 / 인증정보 / **표준카테고리** / 추가정보 / 가격정보 / 속성정보 / 단품정보 / **추가상품정보** / 이미지정보 / **관리자메모** / 상세설명정보. 순서도 다르다(속성정보는 마지막이 아니라 6번째).

### 3.6 재고·상태 동기화의 구멍

- **품절 해제가 자동화 안 된다**: "판매상태(품절) 전송 가능 조건 : 최종 상품송신 상태가 '공급중'인 경우만 가능 — **[일시중지, 완전품절 → 공급중]은 자동화로 송신 불가.**" 재입고를 몰에 자동으로 알릴 수 없다는 뜻이다.
- **옵션 없는 단품은 재고 자동송신 자체가 안 됨.**
- **모음전은 자동 동기화 아님**: 전송 전 `[모음전 현재고/상태동기화]` 수동 클릭 필요. 자동반영 설정(운영환경설정 1-4)은 **가상재고에만** 적용되고, 현재고 기준 운영이면 여전히 수동이다(교차검증 보강).
- **세트Ⅱ는 재고 수량이 반영 안 됨**, 공급상태만.
- 쇼핑몰별 재고분할은 **상품 등록 송신에는 적용 안 되고** 옵션재고 수정송신에서만 반영.
- 스케줄러 사각지대: 00:00~06:00 미실행 + "상품 수정일 **당일**만 실행" + ReadTimeout 5분 초과 시 **비정상종료**.
- 자동화 실행 직전 수동 수정한 상품은 **자동화 대상에서 제외**되고, 특정 상품만 자동화에서 빼는 것도 불가.

### 3.7 사용자가 직접 말한 것 (커뮤니티)

- **주문 누락**: "주문수집 부분이 원활하지 않아 **주문 누락건이 제법 자주 발생**되는 편입니다" — 원인으로 장바구니 담은 날이 주문일로 인식되는 문제 지목. 같은 글: "상품 하나에 여러 사이트로 송신하고 싶은데 한 사이트밖에 송신이 안되는 것 같습니다"([아이보스](https://www.i-boss.co.kr/ab-6141-49053)).
- **역할 축소**: "**사방넷은 너무 복잡해서 등록용으로만**", "메뉴얼이 많아서 언제 저 기능 다 활용할 수 있을까", 직원 교육에 시간 투자 필요([아이보스](https://www.i-boss.co.kr/ab-6141-49689)). **통합관리 솔루션인데 실제로는 등록용으로만 쓰고 주문·CS는 이지어드민으로 병행한다.**
- **UI 복잡·학습곡선**: 서로 다른 4개 진영(경쟁사 스윕, 중립 비교글 바티, 샵링커, 레비오사)이 동일 결론. 사방넷이 무료 화상교육 + 기초/심화 2단계 커리큘럼을 상시 운영하는 것 자체가 방증.

**1. 몰별 오버레이 데이터 모델 (부가정보 상당)**
`ChannelListing.channel = String` 위에 **배송/출고지/반품지 프로필**을 별도 엔티티로 올려야 한다. 사방넷이 (몰 × 계정 × 배송정책) 조합마다 코드를 손으로 만들게 한 지점이다. KidItem은 **배송정책 프로필을 N개 정의 → 몰에 배정**하는 참조 구조로 만들어 조합 폭발을 피해야 한다. 삭제 가능해야 하고, 대량 편집 가능해야 한다.

**2. 전송 잡 큐 + 정직한 상태기계**
`PENDING → SENDING → SUCCESS / FAILED / UNKNOWN(검증필요)` 5-state. **`SUCCESS`는 몰 상품코드를 회수했을 때만.** 코드를 못 받으면 `UNKNOWN`이고, 등록 후 몰에서 재조회해 유령 성공/실패를 판정하는 **검증 워커**가 반드시 붙어야 한다. 사방넷의 "성공 여부와 무관하게 처리완료"를 그대로 베끼면 안 된다.

**3. 재전송 멱등성 키**
`(productId, channel, channelAccountId)` 기준 idempotency key로 중복 등록을 원천 차단. 사방넷의 "여러 번 재송신하면 중복 등록될 수 있습니다"가 그대로 재현되면 실패다.

**4. 실패 카탈로그 + 인라인 수정 재전송**
사방넷의 `[쇼핑몰상품등록(실패)]` 전용 큐 개념은 좋은 설계다. 여기에 **몰별 에러 코드 → 정규화된 사유 분류 → 화면에서 즉시 수정 → 재전송**까지 붙여야 한다. 사방넷은 "상품명, 판매가, 브랜드명은 화면에서 수정하여 재전송 가능"까지만 한다.

**5. 큐는 스냅샷이 아니라 참조**
예약 실행 시점에 상품 마스터를 **다시 읽어야** 한다. 사방넷의 스냅샷 큐 문제를 반복하지 말 것.

### P1 — 27개 몰이 되려면 필요

**8. 옵션/재고/품절 송신 — 특히 품절 해제**

## 5. KidItem이 이길 수 있는 지점

**"AI로 더 좋게"는 답이 아니다. 사방넷도 이미 AI 카테고리 추천(2025-05, 12개 몰), AI 상품정보고시 생성, AI 스마트 상품매칭을 붙였다.** 이기려면 사방넷이 구조적으로 못 하는 곳을 쳐야 한다.

### 5.1 커버리지 — 사방넷이 붙일 수 없는 몰 (최강 해자)

온채널·꼬망세·키드키즈·보리보리는 **사방넷 목록에 존재하지 않는다.** 아이스크림복지몰·키즈노트(구)는 레거시 `-` 상태다. 그리고 사방넷의 신규 몰 편입은 셀프서비스가 아니라 **제휴 협의 + 연동개발**이다. 셀러가 요청한다고 붙지 않는다.

KidItem은 이미 이 몰들의 주문수집 파이프라인을 확장 화면 자동화로 만들어 뒀다(온채널 POST 리버스, 꼬망세 EduPre export, 키드키즈 logis_down5 POST, 보리보리 excel-xlsx, 도매꾹 CDN CSV…). **상품등록은 같은 리버스 엔지니어링 근육을 방향만 바꿔 쓰는 일이다.**

> 그리고 사방넷 자체도 "사방넷 클라이언트 PC 프로그램 + 몰 SCM 로그인 계정"에 의존한다. **화면 자동화 방식이라서 열등하다는 논리는 성립하지 않는다.** 차이는 방식이 아니라 커버리지와 관측 가능성이다.

**제품 결정:** 27개 몰 등록 확장에서 **사방넷 미지원 6개 몰을 1순위로** 붙여라. 여기서는 비교가 아니라 독점이다.

### 5.2 전송 관측성 — 사방넷의 최대 결함을 정면으로

사방넷 사용자가 겪는 것:
- '처리완료'인데 등록 안 됨
- '실패'인데 몰에는 등록됨 → 고객센터 티켓
- 재전송하면 중복
- 팝업 닫으면 기록 자체가 없음

**KidItem이 만들 것 — "전송 원장(ledger)"**:
- 몰별 전송 1건 = 1 레코드. 요청 페이로드, 응답 원문, 몰 상품코드, 재시도 이력, 소요 시간 전부 보관.
- **등록 후 검증 워커**: 확장이 몰에서 상품을 재조회해 실제 존재 여부 + 발급 코드를 확인. 사방넷이 GS Shop·패션플러스에서 못 하는 바로 그것.
- **유령 상태 자동 해소**: `UNKNOWN` → 재조회 성공이면 `SUCCESS` + 코드 매핑 자동 생성. 사방넷은 이걸 사람이 온라인 문의로 해결한다.
- **27개 몰 전송 상태 보드**: 몰별 O/X/진행중/유령 한 화면. KidItem은 이미 주문수집 쪽에 "전체수집 → 실패몰 재수집 버튼 동적 노출" 패턴이 있다. **그 UX를 상품등록에 그대로 이식하면 된다.**

이건 AI가 필요 없다. 그런데 사방넷이 20년 못 고쳤다.

### 5.3 AI — 정확도 경쟁이 아니라 "검수 가능성" 경쟁

경쟁사 3사 모두 AI 카테고리 추천을 냈지만 **아무도 정확도를 공개하지 않았고**, 플레이오토는 틀렸을 때 롤백이 "판매취소 후 재등록"이다. **셀러가 자동 추천을 못 믿는 이유는 정확도가 아니라 되돌릴 수 없어서다.**

KidItem이 이미 가진 AI 파이프라인(상품명·상세페이지·썸네일)에 붙일 것:

**(a) 근거 있는 카테고리 제안**
- 27개 몰 카테고리 트리를 도메인 한정으로 수집 → KidItem 표준카테고리 1개에 매핑
- 제안마다 **신뢰도 + 근거**(어떤 몰의 어떤 유사상품이 이 카테고리에 있는지) 표시
- **신뢰도 구간별 게이트**: 고신뢰=자동 확정, 중간=검수 대기, 저신뢰=차단. 사방넷 스마트매칭이 100%/98%/85% 구간으로 하는 것과 형태는 같지만, KidItem은 **몰 전송 전에** 게이트를 건다는 게 다르다.
- **전송 전 dry-run 프리뷰**: 27개 몰에 어떤 카테고리·어떤 상품명·어떤 가격으로 나가는지 한 화면 표. 사방넷에 없는 것.

**(b) 몰별 상품명 자동 변형 (여기가 진짜 차별점)**
사방넷은 몰별 상품명을 **엑셀로 몰별 파일을 따로 만들어** 올리게 한다. KidItem은 AI 상품명 파이프라인이 이미 있으므로, **마스터 상품명 1개 → 몰 규칙(쿠팡 공백포함 120자·표준 상품명 구조, 몰별 금지문자, 몰별 키워드 관행) 적용 → 27개 변형 자동 생성 + 검수 화면**이 가능하다. 이건 사방넷 구조상 못 한다(오버레이가 정적 데이터라서).

**(c) 정보고시·KC 인증 자동 채움**
사방넷은 템플릿 100개 상한 + 건별 적용 + 대량등록 시 적용 불가다. 실무에서는 고시를 전부 "상세 설명 참조"로 채우는 관행이 있고, 사방넷 기본값이 그걸 뒷받침한다("속성 항목 내용을 입력하지 않고 저장한 경우, 기본 값인 '상세 설명 참조'로 자동 저장"). **어린이제품은 KC 인증이 필수라 이 관행이 위험하다.** KidItem이 어린이제품 고시 분류를 도메인 지식으로 자동 판정하고, 상세페이지/공급사 자료에서 인증번호를 추출해 채우면 규제 리스크 자체가 세일즈 포인트가 된다.
※ 단, 사방넷이 안전인증DB(safetykorea)와 자동 대조하는지는 **확인 안 됨** — 매뉴얼상으로는 사용자 직접 입력이다.

**(d) 상세페이지 — 이미지호스팅 의존 탈출**
사방넷은 상세설명 이미지를 자사 이미지호스팅 URL로 삽입하고, "💡 이미지호스팅 서버에서 이미지가 삭제되면 상세페이지에서도 삭제됩니다" + 품번당 22MB 상한 + "ctrl+c/v와 drag/drop 기능은 제공되지 않습니다"라는 낡은 에디터를 쓴다. KidItem은 상세페이지를 AI로 생성하므로 **소스가 데이터고 렌더가 산출물**이다. 몰별 재생성이 가능하고 벤더 호스팅에 락인되지 않는다.

### 5.4 세팅 제로 — 30일을 하루로

운영사 자인 30일, 대행 시세 몰 10개×상품 150개에 30만원. 이 비용의 정체는 **부가정보/카테고리/매핑 조합을 손으로 만드는 일**이다.

KidItem이 할 것:
- **배송정책 프로필 N개 → 27개 몰 자동 배정** (사방넷은 조합마다 코드 생성)
- **기존 몰 상품에서 역방향 추론**: KidItem은 이미 `product-hub/matching` 역매핑 화면과 이름매칭 파이프라인(정규화→완전일치→포함→퍼지 LCS/Dice + 가격 가드)이 있다. 사방넷의 상품 수집 지원은 **6개 몰뿐**이고, 대행업계는 "역매핑 특성상 각 쇼핑몰의 상품을 사방넷에 전부 등록하는 방식"이라 몰별 중복 마스터가 기본이며, 1상품=1마스터로 합치는 건 **추가 유료 옵션**이다. **KidItem은 처음부터 SKU 기준 통합을 기본값으로 두면 된다.**
- **몰별 필수 필드 사전 검증**: 전송 전에 "쿠팡은 X가 없어서 실패할 것"을 미리 알려주기. 사방넷은 보내봐야 안다.

### 5.5 요금 구조 — 정직한 축

사방넷: 월 15만~235만 + 가입비 10만~100만 + 스케줄러 3~5만 + API 5만~50만. "안 쓰는 기능까지 값을 낸다"는 불만이 반복된다. 자사 시스템인 KidItem에는 직접 해당하지 않지만, **외부 판매를 고려한다면 "채널 수 과금 없음 / 자동화는 기본 포함"이 그대로 메시지가 된다.**

### 5.6 이기지 못하는 곳 — 솔직히

- **몰 수 총량**: 696 vs 27. 여기서 싸우면 진다. **"유아·교육 커머스 전용"으로 프레임을 좁혀야 한다.**
- **범용 카테고리 커버리지**: 전 카테고리 셀러는 사방넷을 쓴다.
- **성숙도**: 클레임·CS·정산 대사 기능은 사방넷이 앞선다. 특히 정산은 사방넷이 "쇼핑몰 정산 데이터 ↔ 사방넷 배송완료 데이터 대조"(reconciliation)로 정의하는데, KidItem의 판매현황 대시보드는 아직 보고서 수준이다.

## 6. 상품등록 확장에 대한 직접 시사점

### 6.1 배울 점 (설계에 그대로 가져올 것)

| 사방넷 설계 | 왜 좋은가 | KidItem 적용 |
|---|---|---|
| **마스터 + 몰별 오버레이 2층** | 공통/몰별 정보를 섞지 않음 | `ChannelListing`에 오버레이 필드셋 추가. 오버레이 없으면 마스터 값 폴백(사방넷과 동일) |
| **실패 전용 큐** | 실패가 성공 목록에 묻히지 않음 | 실패 워크스페이스 + 사유별 그룹 + 인라인 수정 |
| **임시상품 확정 게이트** | 업로드와 커밋 분리 → 검토 기회 | 대량 등록 시 `DRAFT → 검토 → COMMIT` |
| **예약 큐(비동기 배치)** | 27개 몰 순차 처리를 사람이 안 기다림 | KidItem은 이미 주문수집에 동시성 풀(`COLLECT_ALL_CONCURRENCY=4`)이 있음 — 그대로 재사용 |
| **표준카테고리** | 마스터→멀티몰 매핑의 정답 형태 | 도메인 한정이라 사방넷보다 훨씬 높은 커버리지 가능 |
| **옵션 문자열 몰별 치환 사전** | 몰마다 다른 표기를 데이터로 흡수 | 단순하지만 필수 |
| **EA(출고 배수)** | 주문수량 ≠ 출고수량 문제를 필드로 해결 | 교구 세트에 유용 |
| **쇼핑몰 특이사항 버튼** | 몰별 예외를 제품 안에 문서화 | 몰별 제약·위험도를 코드 메타데이터로 |

### 6.2 피할 점 (반대로 만들 것)

| 사방넷 실패 | KidItem 반대 설계 |
|---|---|
| "성공 여부와 무관하게 처리완료" | **몰 상품코드 회수 = 성공.** 못 받으면 `UNKNOWN` + 검증 워커 |
| 유령 실패 → 고객센터 티켓 | 등록 후 몰 재조회 자동 판정 |
| "여러 번 재송신하면 중복 등록" | **멱등성 키 필수.** 재시도가 안전해야 재시도 UI가 의미 있음 |
| 예약 큐 스냅샷 | 실행 시점 마스터 재조회 |
| "몰별로 1~3 반복" | **1회 선택 → 27개 몰 팬아웃.** 몰별 설정 차이는 UI가 아니라 오버레이가 흡수 |
| 부가정보 대량등록 불가·삭제 불가 | 프로필 참조 구조 + 대량 편집 + 삭제 가능 |
| 3단옵션·모음전을 등록 후에만 | **1패스 완결.** 등록 화면에서 전부 입력 |
| 정보고시 템플릿 대량 적용 불가 | 대량 등록/수정에도 템플릿 적용 |
| 완전품절 = 일부 몰 영구 삭제 (경고만) | **몰별 위험도 메타데이터 + confirm 게이트 + dry-run**. KidItem이 송장 등록에서 쓰는 원칙 그대로 |
| 팝업 닫으면 기록 없음 | 모든 전송 시도를 서버측 원장에 기록. UI 세션과 무관 |
| 카테고리 3중 경로 + 우선순위 규칙 | **경로 1개.** 우선순위 규칙이 필요한 시점이 곧 설계 실패 |
| 자동화 실행 직전 수동 수정 = 대상 제외 | 수동/자동 전송이 같은 큐를 쓰도록 |
| 품절 해제 자동화 불가 | 상태 전이를 **양방향 대칭**으로 |
| 00:00~06:00 미실행 + "수정일 당일만" | 시간 창 제약 없이 + **미전송분은 창을 넘겨도 남아 있어야** |
| 다국어·특수기호 인코딩 오류 | UTF-8 일관 + 몰별 금지문자 사전 검증 |

### 6.3 실행 순서 제안

1. **몰 2~3개로 전송 원장 + 검증 워커부터 만든다.** 쿠팡 WING(이미 있음) + 사방넷 미지원 몰 1개. 27개를 얕게 붙이는 것보다 **"전송이 성공했는지 진짜로 아는" 구조**를 먼저 세우는 게 중요하다. 이게 3.1의 공격 지점이고, 나중에 소급 적용이 가장 어렵다.
2. **오버레이 모델 + 배송 프로필**을 그 2~3개 몰로 검증. 조합 폭발이 KidItem 설계에서 안 나는지 확인.
3. **사방넷 미지원 6개 몰(온채널·꼬망세·키드키즈·보리보리·아이스크림·키즈노트)** 을 그다음. 여기가 독점 구간.
4. **표준카테고리(도메인 한정) + AI 제안 + 신뢰도 게이트**를 몰 수가 10개를 넘길 때 투입. 그 전에는 수작업 매핑이 더 빠르다.
5. 몰별 상품명 AI 변형, 정보고시 자동 채움은 그 위에.

**하지 말 것: 27개 몰에 동시에 등록 기능을 얕게 까는 것.** 사방넷이 696개 중 상품등록 O가 332개, 활성 361개 중에도 기능이 들쭉날쭉한 이유가 이거다. 몰마다 실제로 되는 범위가 다르고, 그걸 숨기면 "연동됨인데 안 됨"이라는 사방넷과 같은 신뢰 문제가 생긴다. **몰별 지원 기능 매트릭스를 제품 안에 노출하라.**

## 7. 확인되지 않은 것

정직하게. 아래는 **근거를 못 찾았거나 출처가 상충하는** 항목이다. 의사결정에 쓰기 전에 별도 확인 필요.

### 7.1 사방넷 제품 자체

- **상품등록 쿼터 계산 방식**: 리셀러 페이지의 "상품등록 2,000~100,000건"이 '상품 1건 = 1카운트'인지 '상품 × 몰 = N카운트'인지 **명시 근거 없음.** 몰별 반복 송신 구조상 후자일 가능성이 있으나 확증 없음. 게다가 현행 공식 요금 API에는 상품송신이 전 등급 무제한(-1)으로 나와 **리셀러 페이지가 레거시일 가능성이 높다.**
- **상품명·상세설명 바이트 상한**: "사방넷은 상세설명 항목에 바이트 수 제한 있음"이라고만 적혀 있고 **실제 숫자 미공개.** 확인된 건 옵션 변환 문자열 1,500Byte뿐.
- **'쇼핑몰특이사항' / '필독 상품등록정보' 실제 내용**: 로그인 필요로 접근 불가. **어떤 몰이 상품등록 송신 자체를 지원하지 않는지 정확한 목록 미확보.**
- **등록 실패 사유 코드 전체 목록**: 사례(속성정보 미등록, GS Shop·패션플러스 유령 실패)만 확보. 체계적 에러 카탈로그 없음.
- **사방넷 API 3.0으로 외부 시스템이 상품등록을 프로그래매틱하게 밀어넣을 수 있는지**: 공개된 RTL_API 가이드에는 상품등록&수정, 상품요약수정(재고), 카테고리 관리 등이 있으나 **OMS 본체의 주문/송장/클레임 API 3.0 스펙은 비공개**(계약 후 제공 추정).
- **속성정보 신규등록 가능 여부의 최종 확정**: 사방넷 공식 문서끼리 모순 상태(FAQ는 불가, 매뉴얼·PDF는 가능). **실제 계정 화면에서 `[속성등록&수정]` 버튼이 저장 전 활성인지 라이브 확인 못 함.**
- **몰별 연동 방식(공식 API / 화면 자동화 / 엑셀) 구분**: 사방넷 공개 API 응답에 '연동 방식' 필드 자체가 없음. 아임웹 사례처럼 ID/PW와 API키를 동시에 요구하는 폼 구조가 간접 증거이나, **특정 몰이 실제로 어떤 경로로 통신하는지 확인 불가.** 사방넷이 스크래핑을 쓴다는 직접 증거도 못 찾음.
- **`-` 335건의 공식 의미**: 사방넷이 정의한 문서 없음. 구/신 쌍 패턴으로 추론한 것.
- **연동몰 카테고리 분포 불일치**: 같은 696 합계에 대해 두 번의 조회에서 유형별 분포가 다르게 나옴(오픈마켓 68 vs 89 등). 원인 확인 안 됨.
- **표준카테고리 총 분류 수, 매칭카테고리 커버리지(%), 매칭 실패 시 폴백 규칙**: 매뉴얼 PDF가 로그인 뒤에 있음.
- **정보고시 속성분류코드 전체 코드표**: [014] 내비게이션, [032] 물품대여, [034] 상품권/쿠폰 3개만 간접 확인. **어린이제품·완구 카테고리의 고시 분류 코드와 필수 항목은 미확인** — KidItem 도메인에 직결되므로 우선 확인 필요.
- **KC 인증정보를 안전인증DB와 자동 대조하는 기능 유무**: 근거 없음. 매뉴얼상 사용자 직접 입력 + 쿠팡 수집 시에만 값 이관.
- **스마트상품매칭 실제 정확도 분포·지원 77개 몰 목록**: 로그인/다운로드 필요.
- **안전재고수량 필드가 자동 품절 트리거인지 표시용인지**: 필드 존재만 확인, 동작 미확인.
- **몰별 재고분할 지원 몰 목록**: 스마트스토어 예외만 언급되고 표 없음.
- **스케줄러가 무료 기본인지 유료인지**(문서 간 상충): 사방넷 공식 사이트 FAQ·소개 페이지는 유료 부가서비스(월 3만/5만)로 명시하나, 매뉴얼에는 자동화서비스Ⅱ에만 유료 표기가 있고 스케줄러에는 없음.
- **자동화서비스Ⅰ·Ⅱ 차수가 도는 실제 시각과 차수별 요금**: 로그인/견적 영역.

### 7.2 시장·가격

- **공신력 있는 시장 점유율 통계 없음.** "사방넷 80% 점유"는 블로그의 업계 추정치이며 통계기관 자료 아님. 셀러 수도 출처마다 6,000곳/7,000곳/집계 기준 불명.
- **사방넷 공식 '세팅 서비스' 현행 가격표**: 약관에 "버전별 요금 + 추가 서비스 개수"라고만 있고 견적 화면은 로그인 필요. 2021년 출시 보도(30일→7일)만 확보.
- **다우IDC 리셀러 가격표가 현행인지 레거시인지 확정 못 함.** 상품명·몰 수 표기가 공식과 불일치.
- **경쟁사 요금**: 셀메이트 공식 요금표 403, 이지어드민 가격 미게시(상담 유도), 넥스트엔진 코리아 현재 운영 여부 403으로 확인 실패.
- **프로모션 검증 실패**: "이커머스페어 사용료 3만원 + 가입비 면제", "토스쇼핑 제휴 미니 월 1,000원" 등은 검색 스니펫만 있고 1차 출처 접근 불가.
- **미니→본품 업그레이드 시 데이터 이관 비용·가입비 면제 여부, 다운그레이드 가능 여부**: 문서 없음.

### 7.3 사용자 불만 쪽

- **1인칭 해지 사유 글을 사실상 못 찾음.** 비판 자료 대부분이 경쟁사 비교 콘텐츠나 대행사 랜딩페이지라 이해관계가 섞여 있다. 순수 사용자 증언은 아이보스 2건이 거의 전부이며, **이 보고서의 "주문 누락이 제법 자주"도 셀러 1명의 진술이다.**
- **네이버 카페 셀러 커뮤니티 접근 실패.** 실제 불만의 상당량이 여기 있을 것으로 보이나 미확인.
- **'사방넷과 메이크샵 연동 오류 정리'(가격수정·제품명 수정·품절관리 미작동, 메이크샵 데이터 삭제)** — 원문 404. 검색엔진 추출 요약만 있어 **신뢰도 낮음. 인용 시 주의.**
- **카페24 연동 현재 상태 상충**: 카페24 헬프센터는 "API 연동 안 됨 / 정식 제휴 아님"인데 앱스토어에는 사방넷 앱 등재. **작성 시점 확인 필요.**
- **공식 장애/다운타임/SLA 문서 없음.** 안정성 지표 확인 불가.
- **쿠팡 로켓그로스 지원 여부 확인 불가** (플레이오토·넥스트엔진은 문서 있으나 사방넷은 없음). 미지원이면 강력한 차별화 포인트인데 **근거 없음.**
- **몰별 클레임 수집 지원 범위(취소/반품/교환) 몰 단위 표 없음.** 3PL 가이드는 자기 연동 기준만 말한다("취소는 되고 반품·교환은 안 된다").
- **몰별 송장 전송 실패 시 재시도·부분 실패 처리 로직**: 2026-04 고도화로 "완료·실패 팝업/알림톡/문자"가 생겼다는 것 외 세부 비공개.
- **정산 기능의 실제 입력 방식(API인지 엑셀 업로드인지)** 미확인.
- **다우기술 내부 시각(채용공고 기술스택, 조직 규모)** 확보 실패 → "레거시라서 못 고친다" 가설은 **검증 안 됨.**

### 7.4 방법론상 한계

- 사방넷 공식 문서 호스트(`docs.sabangnet.co.kr:1975`)는 **TLS 중간 인증서 체인이 불완전**해 표준 fetch가 실패한다. 본문은 인증서 검증을 우회해 취득했다. 내용 자체는 정상 확인됐다.
- 교차검증 세션에서 웹 검색 예산이 소진되어, 일부 항목(22MB 상한, 임시상품 삭제, 4,000개 권장 등)은 **사방넷 공식 문서 내 서로 다른 페이지 간 대조까지만** 이뤄졌고 제3자 출처 확인은 못 했다.
- 파괴적 동작(완전품절 = 영구삭제, 임시상품 삭제)은 **문서 근거로만 판정했고 실계정 재현 검증은 하지 않았다.**
