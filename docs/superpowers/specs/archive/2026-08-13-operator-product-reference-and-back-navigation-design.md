# 운영자용 상품 식별자와 상세 복귀 동작 설계

- 상태: 승인됨
- 작업: KID-23
- 날짜: 2026-08-13

## 배경

Sellpia 재고에서 자동 생성된 `MasterProduct`는 동기화 연결을 유지하기 위해
`INV-SELLPIA-<UUID>` 형식의 내부 코드를 사용한다. 채널 원본 상품도
`CP-<UUID>` 계열의 내부 코드를 가진다. 이 값들은 데이터 연결에는 필요하지만 현재
상품 목록, 상품 상세, 수정 화면, 재고 매칭, Sellpia 재고 연결 목록에서 운영자용
상품 식별자처럼 노출될 수 있다.

또한 `/product-hub/[id]`의 상단 복귀 링크는 진입 경로와 관계없이
`/product-hub`로 이동한다. Sellpia 재고나 다른 운영 화면에서 상세로 들어온 사용자는
직전 작업 화면과 URL 상태를 잃는다.

## 목표

1. 시스템이 생성한 상품 코드를 데이터 식별자로 유지하되 운영자 UI에서는 숨긴다.
2. 운영자가 지정한 상품 코드, Sellpia SKU, 채널 상품번호 등 업무에 필요한 식별자는
   계속 표시한다.
3. 숨김 정책을 공유 frontend utility 한 곳에서 판별하여 적용 화면마다 규칙이
   달라지지 않게 한다.
4. 상품 상세의 복귀 버튼은 실제 브라우저 직전 이력으로 돌아가며, 이력이 없는 직접
   진입만 상품 카탈로그로 대체한다.

## 비목표

- 내부 코드를 데이터베이스나 API 응답에서 제거하지 않는다.
- `MasterProduct.code` 생성 규칙, Sellpia 동기화, 상품·재고 매칭 관계를 변경하지
  않는다.
- 운영자가 입력한 일반 상품 코드나 채널에서 제공한 공개 상품번호를 숨기지 않는다.
- 모든 상세 링크에 `returnTo` query parameter를 추가하지 않는다.
- Sellpia SKU 코드, 옵션 코드, 바코드, 채널 외부 상품번호의 검색 기능을 제거하지
  않는다.

## 검토한 접근

### 1. 공유 frontend 정책으로 내부 코드만 숨기기

내부 코드 namespace를 판별하는 pure utility를 만들고 모든 상품 운영 UI가 이를
사용한다. 백엔드 식별 관계는 유지하면서 현재 요구인 화면 정리를 한 곳의 정책으로
보장할 수 있어 이 방식을 채택한다.

### 2. API 계약에서 표시 가능 여부를 추가하기

표시 정책을 backend projection으로 강제할 수 있지만 Products, Inventory, Matching의
서로 다른 응답 계약을 함께 변경해야 한다. 내부 식별자를 API 소비자에게서 제거하는
작업은 이번 UI 범위를 넘어선다.

### 3. 상세 링크마다 복귀 URL을 전달하기

복귀 목적지를 명시할 수 있지만 모든 진입 링크와 query serialization을 수정해야
한다. 브라우저 이력이 이미 직전 화면의 필터, 페이지, 탭을 정확히 보존하므로 별도
복귀 상태를 만들지 않는다.

## 내부 코드 표시 정책

공유 `operator-product-reference` utility가 다음 namespace를 내부 코드로 판별한다.

- Sellpia 동기화 원본: `INV-SELLPIA-*`
- 채널 원본용 UUID 코드: `CP-<UUID>` 및 `CP-SKU-<UUID>`

판별은 대소문자와 앞뒤 공백을 정규화한다. 내부 코드이면 상품명만 표시하거나 상품
코드 행·배지를 생략한다. 내부 코드가 아니면 기존 `코드 · 상품명` 또는
`레이블 값` 표시를 유지한다. `displayReference.type`이 `channel_product`인 경우에는
내부 `MasterProduct.code` 대신 채널이 제공한 상품번호를 계속 표시한다.

이 정책을 다음 운영 UI에 적용한다.

- 상품 운영 목록의 상품 보조 정보
- 상품 상세 헤더와 `상품 운영 정보` 카드
- 상품 정보 수정 dialog
- 상품 재고 매칭의 연결 상품 요약
- `셀피아 재고` 탭의 연결 상품 목록

상품 수정 dialog에서 내부 상품은 코드 입력 필드를 렌더링하지 않는다. 수정 payload는
기존 코드를 그대로 보존하여 이름, 카테고리, 브랜드 등의 변경이 동기화 식별자를
훼손하지 않게 한다.

## 상품 상세 복귀 동작

상세 헤더의 고정 `/product-hub` 링크를 `이전 화면` 버튼으로 바꾼다. 클릭 시
브라우저 이력이 있으면 Next router의 `back()`을 호출한다. 따라서 상품 목록의 검색과
페이지, `셀피아 재고` 탭의 필터와 pagination, 다른 운영 화면의 상태가 브라우저가
보존한 그대로 복원된다.

현재 문서가 첫 history entry라서 돌아갈 이력이 없으면 `replace('/product-hub')`를
사용한다. 이 fallback은 직접 진입에서도 안전한 목적지를 제공하고 상세 화면으로 다시
돌아오는 history loop를 만들지 않는다. 데이터 로딩과 오류 처리에는 영향을 주지
않는다.

## 데이터 흐름과 오류 처리

API 요청과 응답 schema는 변경하지 않는다. 내부 코드 판별은 렌더링 직전의 pure
frontend 정책이며 식별자 값 자체를 mutation하지 않는다. 빈 값이나 예상하지 못한
일반 코드는 숨기지 않고 기존 표시를 유지하여 잘못된 범위 확장을 피한다.

복귀 버튼은 네트워크 요청을 만들지 않는다. history fallback도 client navigation만
사용하므로 별도 오류 UI가 필요하지 않다.

## 테스트 전략

구현은 TDD 순서를 따른다.

1. 공유 utility가 `INV-SELLPIA-*`, `CP-<UUID>`, `CP-SKU-<UUID>`를 내부 코드로
   판별하고 일반 상품 코드는 유지하는 실패 테스트를 작성한다.
2. 상품 목록과 상세의 내부 코드가 보이지 않지만 일반 상품 코드와 채널 상품번호는
   보이는 실패 테스트를 작성한다.
3. 내부 상품의 수정 dialog가 코드 입력을 숨기고 기존 코드를 보존해 저장하는 실패
   테스트를 작성한다.
4. 재고 매칭과 `셀피아 재고` 연결 목록이 내부 코드 대신 상품명만 표시하는 실패
   테스트를 작성한다.
5. 상세 복귀 버튼이 history가 있으면 `router.back()`을 호출하고, 이력이 없으면
   `/product-hub`로 replace하는 실패 테스트를 작성한다.
6. 최소 구현 후 product-hub, inventory-hub 관련 테스트와 frontend build를 실행한다.
7. 브라우저에서 내부 Sellpia 상품의 목록·상세·수정 화면과 직전 화면 복귀를 확인한다.

## 완료 기준

- 운영자 화면 어디에서도 `INV-SELLPIA-*` 또는 UUID 기반 `CP-*` 내부 코드가
  표시되지 않는다.
- 일반 상품 코드, Sellpia SKU, 채널 상품번호는 기존처럼 확인하고 검색할 수 있다.
- 내부 상품의 메타데이터 수정이 기존 내부 코드를 그대로 유지한다.
- 상품 상세에서 뒤로가면 실제 직전 화면과 해당 URL 상태가 복원된다.
- 직접 진입한 상세의 복귀 버튼은 상품 카탈로그로 안전하게 이동한다.
- 관련 테스트와 `npm run build --workspace=apps/web`이 통과하고 브라우저 검증이
  완료된다.
