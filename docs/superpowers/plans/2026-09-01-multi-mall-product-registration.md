# 수집상품 → 전 쇼핑몰 상품등록 확장

수집상품(SourcingCandidate) 등록 대상을 쿠팡 WING 한 곳에서 운영 중인 27개 몰로
넓힌다. KidItem 이 사방넷과 같은 자리(쇼핑몰 통합관리)를 목표로 하므로, 외부
통합 솔루션을 경유하지 않고 직접 구축한다.

## 지금 상태

| 항목 | 현재 |
|---|---|
| 등록 대상 | 쿠팡 WING 1개 |
| 방식 | 일괄등록 엑셀(`.xlsm`) 생성 → 확장이 WING 화면에 업로드. `fillWingForm` 폼 직접 채움 경로 병행 |
| 코드 | `collected-products/lib/wing-registration-flow.ts` 1,032줄 + `wing-registration-excel.ts` + `wing-category-presets.ts` + `wing-category-resolution.ts` |
| 서버 | `MarketplaceRegistrationService` 존재하나 쿠팡 Open API(`COUPANG_PROVIDER_PORT`) 전용 |
| 데이터 모델 | `ChannelListing.channel` / `ChannelAccount.channel` 이 이미 String — **채널 무관** |
| 계정 | 27개 몰 계정이 `쇼핑몰 설정`에 이미 저장·관리됨 |
| 역매핑 | `product-hub/matching` 이 이미 존재 — 몰 리스팅↔내부 상품 연결 |

데이터 모델·계정·역매핑 기반은 이미 서 있다. 없는 것은 **몰별 등록 실행부**와
**카테고리·필수속성 매핑**이다.

## 참조 모델 — 사방넷

심층 조사 결과는
[사방넷 경쟁 분석](../2026-09-01-sabangnet-competitive-research.md)에 있다. 계획에
직접 영향을 준 것만 옮긴다.

### 구조

사방넷은 **마스터 + 몰별 오버레이 2층**이다. 마스터(품번코드 6자리 + 단품코드
4자리)의 상당 필드는 몰로 전송되지 않고, 실제 전송되는 값은 오버레이에 있다.

| 오버레이 | 단위 | 등록 |
|---|---|---|
| 쇼핑몰부가정보 (**필수**) | 몰 × 계정 × 배송정책 조합 | 건별, **대량등록 불가·삭제 불가** |
| 쇼핑몰카테고리 (선택) | 몰 × 계정 | 몰 SCM 실시간 조회 |
| 쇼핑몰별 별도정보 | 몰별 | 건별 또는 몰별 엑셀 |

전송은 단일 publish 가 아니라 등록/수정/품절/옵션 **5개 메뉴로 분리**돼 있고,
전송 단위가 **상품 N개 × 몰 1개 × 계정 1개**다. 다몰 동시 전송이 없어 몰마다
반복해야 한다. 동기화는 실시간이 아니라 **상품 10분 / 주문 30분 배치이고
00:00~06:00 은 미실행**이며, 대상은 "수정일 당일"분만이다.

그리고 사방넷도 **PC 클라이언트 + 몰 SCM 로그인 계정**에 의존한다. 카테고리
조회조차 몰 로그인으로 실시간 조회한다. **KidItem 의 확장 화면 자동화가 열등한
방식이 아니라는 뜻이다.** 차이는 방식이 아니라 커버리지와 관측 가능성이다.

### 숫자

- 연동 몰 **696개**(라이브 API 실측). 홍보 문구의 650·600·450·200 은 갱신 지연.
- 그중 7개 기능이 전부 `-` 인 레거시 335건을 빼면 **실활성 361개**.
- 기능별: 주문수집 O 343 / **상품등록 O 332** / 송장전송 O 327.
- 요금 월 15만(싱글)~235만(플래티넘) + 가입비 10만~100만. 스케줄러는 별도 월 3~5만.
- **셀프 세팅 기준선 30일** (운영사 자인). 대행 시세는 "몰 10개 × 상품 150개 = 30만원".

### KidItem 채널과의 대조 — 이 계획의 방향을 바꾼 사실

696건 전수 검색 결과 **온채널·꼬망세·키드키즈·보리보리는 사방넷 목록에 아예 없다.**
아이스크림복지몰·키즈노트(구)는 레거시 `-` 상태다. 사방넷의 신규 몰 편입은
셀프서비스가 아니라 제휴·연동개발 협의라서, 작은 몰은 붙을 유인이 없다.

**KidItem 이 이미 주문수집 파이프라인을 만들어 둔 이 6개 몰이 사방넷 커버리지
밖이다.** 상품등록은 같은 리버스 근육을 방향만 바꿔 쓰는 일이다. 여기는 비교가
아니라 독점 구간이므로 **우선순위 1순위**로 둔다.

### 차별화 지점 정정

앞서 "AI 카테고리 매핑이 차별점"이라고 봤으나 **틀렸다.** 사방넷(2025-05, 12개 몰),
샵링커, 플레이오토가 이미 AI 카테고리 추천을 냈다. 레드오션이다.

진짜 빈 자리는 **아무도 "틀렸을 때 어떻게 되돌리는가"를 풀지 않았다**는 것이다.
플레이오토는 카테고리를 잘못 등록하면 롤백이 "판매취소 후 재등록"이다. 셀러가
자동 추천을 못 믿는 이유는 정확도가 아니라 되돌릴 수 없어서다.

그리고 더 큰 빈 자리가 있다 — **전송 관측성**. 사방넷은:
- "상품등록송신시 **실제 등록 성공 여부와 상관없이 '처리완료'로 변경**"
- 유령 실패(몰에는 등록됐는데 사방넷은 실패)의 복구 수단이 **고객센터 티켓**
- "같은 상품을 여러 번 재송신하면 **중복으로 등록될 수 있습니다**"
- 예약 큐가 스냅샷이라 저장 후 상품을 고쳐도 **옛 데이터가 전송됨**

**이건 AI 가 필요 없는데 사방넷이 20년 못 고친 것이다. KidItem 의 최대 공격 지점.**

## 주문수집과 다른 점 (이 계획의 전제)

주문수집은 27개 몰을 같은 패턴으로 반복해 풀었다. 등록은 그 경험을 그대로 쓸 수 없다.

- **읽기가 아니라 쓰기다.** 잘못 등록하면 실제로 팔린다. 되돌리려면 몰마다 내려야 한다.
- **카테고리 체계가 몰마다 완전히 다르다.** 쿠팡 트리와 스마트스토어·11번가 트리는
  서로 대응되지 않는다. 몰당 수천 개다. 폼 채우기가 아니라 이 매핑이 진짜 작업량이다.
- **필수 속성이 다르다.** 아동용품은 KC 인증 정보가 법적 필수인데 요구 형식과 입력
  위치가 몰마다 다르다. 고시정보·원산지·인증번호도 마찬가지다.
- **옵션 구조가 다르다.** 단일/조합형/독립형 지원 범위가 몰마다 갈린다.

## 공통 기반

### 1. 상품 마스터 (몰 중립) + 몰별 오버레이

```
SourcingCandidate
  → ProductRegistrationDraft (몰 무관 = 상품 마스터)
      상품명 / 판매가 / 재고 / 옵션 / 대표이미지 / 추가이미지
      상세 이미지(확정 1장) / 원산지 / 제조사 / KC 인증 / 고시정보
      카테고리: 내부 표준 분류 1개
  + 몰별 오버레이 (없으면 마스터 값 폴백)
      몰별 상품명 / 판매가 / 카테고리 / 고시분류
  + 배송 프로필 (출고지·반품지·배송비·배송정책)
  → 몰별 어댑터가 각 몰 형식으로 변환
```

**배송 프로필은 반드시 참조 구조로 만든다.** 사방넷은 (몰 × 계정 × 배송정책)
조합마다 코드를 손으로 만들게 하고, 대량등록도 삭제도 안 된다. 이 조합 폭발이
세팅 30일의 정체다. KidItem 은 **프로필 N개 정의 → 몰에 배정**으로 두고, 대량
편집과 삭제를 지원한다.

내부 표준 분류를 두는 이유: 몰이 늘 때마다 N×N 매핑이 되지 않도록 항상
`내부분류 → 몰분류` 1:N 으로만 관리한다. 몰 27개면 27벌이지, 27×27이 아니다.

### 2. 전송 원장과 정직한 상태기계 — 이 계획의 핵심

`PENDING → SENDING → SUCCESS / FAILED / UNKNOWN` 5-state.

- **`SUCCESS` 는 몰 상품코드를 회수했을 때만.** 보냈다는 사실은 성공이 아니다.
- 코드를 못 받으면 `UNKNOWN` 이고, **검증 워커**가 몰에서 재조회해 실제 등록
  여부를 판정한다. 사방넷이 GS Shop·패션플러스에서 못 해 고객센터 티켓으로
  넘기는 바로 그 지점이다.
- 전송 1건 = 1 레코드. 요청 페이로드·응답 원문·몰 상품코드·재시도 이력을 남긴다.
  **UI 세션과 무관하게 서버에 기록한다** (사방넷은 팝업을 닫으면 기록이 없다).

### 3. 재전송 멱등성

`(productId, channel, channelAccountId)` 멱등성 키로 중복 등록을 차단한다.
재시도가 안전해야 재시도 버튼이 의미를 가진다. 사방넷의 "여러 번 재송신하면
중복으로 등록될 수 있습니다"를 재현하면 실패다.

### 4. 실패 전용 워크스페이스

몰별 에러를 정규화된 사유로 분류하고, 화면에서 고쳐 바로 재전송한다.
주문수집의 "실패 몰 재수집" UX 를 그대로 이식한다.

### 5. 큐는 스냅샷이 아니라 참조

예약 전송은 실행 시점에 마스터를 **다시 읽는다.** 사방넷은 예약 저장 후 상품을
고쳐도 옛 데이터가 나가고, 그 사실을 알 방법이 없다.

### 6. 몰별 등록 어댑터

```
supports(): 등록 지원 여부
requiredFields(): 이 몰이 요구하는 필수 속성
validate(draft): 보내기 전 사전 검증
submit(draft): 등록 실행 → { externalId, status }
verify(externalId): 몰에서 재조회해 실제 존재 확인
riskFlags(): 파괴적 동작 메타데이터
```

`verify` 와 `riskFlags` 가 사방넷과 갈리는 지점이다. 특히 **완전품절 송신이
ESM옥션·ESM지마켓·11번가·인터파크·고도몰류에서는 영구 삭제**이므로, 이런
몰별 위험을 코드 메타데이터로 박고 confirm 게이트를 건다.

### 7. 사전 검증 게이트

**등록 전에 막는다**: KC 인증 정보 누락, 카테고리 미매핑, 몰별 금지문자,
필수 이미지 규격 미달. 실패를 몰에서 받지 말고 우리가 먼저 잡는다.

### 8. 카테고리 매핑 저장소

몰별 카테고리 트리를 도메인(유아·완구·문구·교구) 한정으로 수집해 보관하고,
`내부분류 → 몰분류` 매핑을 저장한다. AI 제안에는 **신뢰도와 근거**를 붙이고,
신뢰도 구간별로 자동 확정 / 검수 대기 / 차단으로 게이트한다.

**전송 전 dry-run 프리뷰**: 27개 몰에 어떤 카테고리·상품명·가격으로 나가는지
한 화면에서 보여준다. 사방넷에 없는 것이고, "틀렸을 때 되돌릴 수 없다"는
업계 공통 문제의 실질적 해법이다.

## 단계

1단계 사실확정은 완료됐다 →
[27개 몰 등록 방식 조사](../2026-09-01-mall-registration-survey.md).
그 결과로 아래 순서를 확정한다.

### 1단계 — 사실 확정 ✅ 완료
결과 요약:
- 공식 API 로 바로 뚫리는 몰 **9개** (네이버·토스·롯데온·SSG·쿠팡·11번가·ESM·카카오·보리보리)
- 커머스 솔루션이 겹쳐 **어댑터 6개가 몰 10개**를 덮음
- 계정 로그인 없이는 더 진도가 안 나가는 몰 **7개**
- **상품 마스터 원천이 수집상품(4건)이 아니라 쿠팡 리스팅(1,228건)** 임이 확인됨
- KC·고시 필드 15개가 전부 신규 수집 대상

### 2단계 — 규제 게이트 + 마스터 승격 (몰 무관, 선행 필수)
- 상품 마스터에 KC·고시 15개 필드 추가, `kcType` 3분기(안전인증/안전확인/공급자적합성확인)
- 고시 카테고리 매핑 테이블 (완구·교구 → 영유아용품 12항목, 문구 → 기타재화 5항목)
- **쿠팡 리스팅 1,228건을 상품 마스터로 승격** — 브랜드·제조사·카테고리·옵션은 이미 있다
- 전송 원장 + 5-state + 검증 워커 + 멱등성 키
- 기존 쿠팡 플로우를 이 기반 위로 이관

여기가 안 되면 쿠팡 '검증' 버튼과 네이버 등록 제한에서 전량 튕긴다. 인증정보 누락
상품이 거부되는 것은 정상 동작이므로, 재시도가 아니라 **진입 전 게이트**로 막는다.

### 3단계 — 공식 API 저난이도 4몰
네이버 → 토스쇼핑 → 롯데온 → 신세계 SSG. 전부 문서 공개 + 자율 키 발급 + 상품등록
API 실재.

**선행**: 롯데온·네이버·11번가는 호출 IP 화이트리스트 등록이 공통 관문 —
한 번에 신청한다.

### 4단계 — 클러스터 어댑터 3개 → 몰 5개
1. **퍼스트몰 selleradmin** (티처몰 + 체더스) — 자사 확장이 이미 세션·폼 규약을 검증함
2. **shopby BPA** (떠리몰 + 웅진클래스몰) — 떠리몰 엑셀 양식 A~BU 컬럼 확보됨
3. **X2BEE PO** (아이스크림몰 + 하이스토어) — 301 리다이렉트로 단일 인스턴스 실증

### 5단계 — 사방넷 미커버 전략 몰
온채널 · 꼬망세 · 키드키즈 · 지니마켓 · 보리보리(+하프클럽).
외부 솔루션 우회 경로가 없어 직접 구현이 유일하고, 그만큼 방어력이 있다.

함정: 온채널은 출고지/반품지 사전 등록 없이는 상품등록 자체가 불가하고,
승인요청 안 한 상품은 **익일 23:59 자동 삭제**된다.

### 6단계 — 잔여
11번가 · 카카오 · ESM(지마켓/옥션) · GS샵 · 키즈노트.
올웨이즈·베네피아는 통합솔루션 경유가 공식 경로라 자체 개발 ROI 를 먼저 계산한다.

### 7단계 — 재고·가격 동기화 (별도 계획)
사방넷이 못 하는 **품절 해제(완전품절 → 공급중) 자동화**를 처음부터 양방향 대칭으로.

## 지켜야 할 것

- **라이브 등록은 항상 확인 게이트를 거친다.** 일괄 등록 전에 몰별 1건 검증.
- **카테고리 자동 추천은 신뢰도가 낮으면 사용자에게 묻는다.**
- **몰 계정은 `쇼핑몰 설정`이 단일 소유자다.** 등록 쪽에서 자격증명을 따로 두지 않는다.
- **실패한 등록을 성공으로 보고하지 않는다.** 로그인 테스트에서 겪은 함정을
  반복하지 않는다 — "시도하지 않음"과 "성공"을 반드시 구분한다.
- **27개 몰에 동시에 얕게 깔지 않는다.** 몰마다 실제로 되는 범위가 다르다.
  **몰별 지원 기능 매트릭스를 제품 안에 노출한다** — 사방넷의 "연동됨인데 안 됨"
  신뢰 문제를 반복하지 않기 위해서다.
