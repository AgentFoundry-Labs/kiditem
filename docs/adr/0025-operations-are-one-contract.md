# Every operation runs under one contract

Collection attempts, AI generation jobs, ad action executions and registration executions each carried their own table, status vocabulary, token, lease, chunk store, rejection codes and screen endpoint: eight tables, four status spellings, six ways to say "cancelled", twenty-seven copies of the fence, and one hundred and seventy-two attempt routes. Every operation now lives in one `operations` row with one `operation_chunks` store and one `operation_locks` row per key it must not overlap, under a `common/operation` module that owns identity, token, lease, chunk staging, overlap and rejection; an owner registers a kind and plugs in two ports, `plan` (what to do and which lock keys to hold) and `finalize` (what ledger facts to write when the operation finishes). We chose one physical table over one contract on separate tables because the duplication was in the rows as much as the code, and over per-kind lock uniques because owners kept inventing new overlap rules.

## Consequences

A kind is `owner.work` (`channels.wing_catalog`, `orders.coupang_reviews`, `content.thumbnail_generate`, `channels.registration`). Status is one lowercase set shared by database, wire and screen; the first contract ships `executing`, `succeeded`, `failed`, `cancelled`, and `prepared` arrives with server-driven kinds. A lease is thirty minutes, extended by every fenced write, expired lazily at the next read or write, with no sweeper because the Office host is not always on. Ledger facts are written only inside the finish transaction; chunks are staged and deleted in that same transaction whether the operation succeeded or failed. Overlap is a set of lock keys the owner declares at begin, held in `operation_locks` and released on finish or expiry; the unique is `(organizationId, lockKey)` without the kind, so a key can fence across kinds. A key is `org`, `account:<channelAccountId>` for kinds that work through the account's Wing login, or `resource:<site>:<id>` for any other shared session or slot, such as `resource:ad-center:<channelAccountId>` for the ad center and `resource:keyword:<keyword>` for a rank slot. A start that would overlap is refused with `OPERATION_IN_PROGRESS`, and every later fenced write that no longer fits is refused with `OPERATION_FENCE_LOST` and a reason. Owner-specific values live in the operation's `plan` and `result` JSON; a value becomes a column only when the database filters, joins, orders or constrains on it. Other owners refer to an operation by scalar id with an index, never by foreign key. The extension has one operation client; a kind's collector only produces chunks. Old rows are not migrated: a kind writes to `operations` from the day it moves, stops reading its old table, and the old tables are dropped when the last kind has moved. Owner code may not touch operation rows through SQL; a scanner enforces this.

## Considered options

One contract with the tables left in place was rejected once the audit showed the twenty-four partial uniques and sixteen foreign keys on `source_import_runs` were the cost being paid, not the code around them. A `scopeKey` column for overlap was rejected because registration needs three keys and future rules (one collection per Wing login) need keys no single scope expresses. Keeping failed chunks for a week was rejected because it needs a cleanup job the Office host cannot promise to run. Excluding registration executions was rejected because they differ from other kinds only in which columns they use.
