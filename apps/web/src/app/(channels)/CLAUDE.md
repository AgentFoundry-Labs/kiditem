# web/channels — 몰별 상품등록·품절 송신

`app/(channels)/` 는 우리 상품을 몰로 내보내는 방향을 소유한다. 몰에서 우리 쪽으로
들어오는 주문수집 · 쿠팡 로켓은 `app/(orders)/`, 쿠팡 쉽먼트는 `app/(inventory)/` 가
소유하며, 세 그룹은 사이드바 '쇼핑몰 에이전트'에서만 합쳐 보인다. 사이드바 자리가
코드 소유를 옮기지 않는다.

- `/mall-home`: 쇼핑몰 에이전트 홈. 위 줄은 대시보드 3(확인 필요 · 열린 몰 알림 · 로그인
  필요 · 품절 후보, 몰별 상태) : 쇼핑몰 알림판 1 이고, 알림판은 그 줄 높이까지만 선다.
  그 아래 넓게 에이전트 파이프라인(미션 → 감지 → 판단 → 도구 → 사람 승인 → 기억)이
  서고 단계마다 그 단계의 일을 아래로 적는다 — 미션은 첫 칸이다. 일·단계 상태는 코드가
  실제로 하는 일 기준이고, 숫자는 `/mall-channels` 와 같은 판정
  (`_shared/use-mall-capability-rows.ts`)을 읽는다.
- 관찰 기록(`MallOperationOutcome`)은 로그인 확인 · 로그인 테스트 · 등록 폼 채움 · 품절 지목만
  한 줄씩 남는다. 결과가 난 자리(로그인 확인 · 로그인 테스트 · 등록 실행기 · 품절 관리)에서 웹이 한 번 쓰고
  (`src/lib/mall-operation-outcomes-api.ts`), idempotencyKey 로 한 번만 저장된다. 주문수집 ·
  셀피아 전송 · 송장 전송 결과는 Orders 가 가진 사실이라 여기 쓰지도 읽지도 않는다. 폼을
  채운 것은 `attention`(제출은 사람)이지 성공이 아니다. 비밀번호 · 받는 사람 · 주문번호는
  담지 않는다 — 개수와 이유 코드만. 화면에서는 '관찰 기록'이라고 부른다.
- 쇼핑몰 알림판은 알림 저장소를 새로 만들지 않는다. 서버 알림은 전역 알림 쿼리
  (`/api/alerts`)에서 몰에서 일하는 원천(`sourceType`)의 실패 알림만 골라 읽고
  (`mall-home/lib/mall-alerts.ts`), 지금 상태 알림(로그인 정보 · 품절 후보 · 쿠팡
  발주확인)은 저장하지 않고 열 때마다 센다. 원천 알림은 원천이 다시 성공하면 닫힌다.
  몰 표시는 원천이 한 몰 것일 때만 한다 — 메시지 글자에서 몰 이름을 짐작하지 않는다.
- 자동 운전(에이전트 고리)은 앱 전역 `MallAgentLoopProvider` 가 돌리고, 쇼핑몰 홈의
  자동 운전 카드는 그 상태를 보여 주고 시작하고 멈출 뿐이다. 고리는 읽고 모으는 일만 한다 —
  전송 · 제출 · 삭제는 사람이 그 화면에서 누른다.
- 고리는 앱을 열었다고 스스로 돌지 않는다. 운영자가 시작하면 곧바로 한 바퀴를 돌고 그 탭이
  열려 있는 동안 정한 간격마다 돈다. 켜짐과 다음 바퀴는 저장하지 않는다 — 새로고침하거나
  탭을 닫으면 멈추고 운영자가 다시 시작한다. 간격과 마지막 한 바퀴만 저장한다.
- 위 칸 숫자(확인 필요 · 로그인 필요)는 서버와 확장이 확인한 사실만 센다. 자동 로그인 차단처럼
  이 브라우저에만 있는 값은 알림판과 몰 타일에는 보이지만 숫자에 섞지 않는다. 품절 후보
  칸은 레시피가 없어 판정할 수 없는 옵션 수를 따로 적는다.
- 같은 사건이 알림과 관찰 기록에 두 번 남는다. 타일은 둘 중 **할 일을 이름으로 부르는 쪽**을
  고른다. 원천 실패 알림은 '실패'라고만 해서 인증인지 로그인인지 말하지 못하고,
  그게 몇 초 늦게 찍혔다는 이유로 이기면 사장님은 무엇을 해야 할지 알 수 없다.
- 로그인 칩은 확장이 본 것만 말하되, 관찰 기록이 본인확인 · OTP 를 기다린다고 하면 `verification`
  으로 덮는다. 세션이 살아 있어도 몰이 인증을 요구하면 '로그인됨'은 거짓말이다.
- 몰 로그인 상태는 로그인됨 · 인증 필요 · 로그인 필요 셋뿐이다(사장님 2026-09-17). 쇼핑몰
  홈을 열 때 확장이 몰마다 정해진 읽기 전용 주소를 읽고, 그걸로 모르면 관리자 화면을
  백그라운드 탭에 열어 로그인 폼 · 인증 화면을 본 뒤 닫는다(`src/lib/mall-session-probe.ts`,
  확장 `mallLoginCheckV2`). 고정 주소가 없는 몰은 쇼핑몰 계정의 사이트 주소를 넘긴다.
  로그인하지 않고 자격증명을 넘기지 않는다. 확인할 주소가 없거나 화면에 닿지 못한 몰은
  로그인 필요로 서되 이유를 함께 두고, 몰을 본 결과가 아니라 관찰 기록에 남기지 않는다.
  나머지 결과는 상태가 바뀌었거나 6시간이 지났을 때만 관찰 기록(`login_check`)에 남는다.
  로그인됨 칩은 확인한 시각(시:분)을 적고, '실패만 다시 확인'은 로그인 필요 · 인증 필요 몰만 다시 본다.
- 로그인 필요 · 인증 필요 타일을 누르면 알림판을 거르지 않고 그 몰 하나만 쇼핑몰 계정 화면의
  로그인 테스트(`useMallLoginTest`, 확장 `testMallLogin`)로 로그인을 다시 해 본 뒤 그 몰만 다시
  확인한다. 사람이 누를 때만 로그인하고, 한 번에 한 몰이다. 확인 자체는 여전히 로그인하지 않는다.
- `/mall-channels`: 연결된 몰 현황 허브. 읽기 전용이고 자격증명을 편집하지 않는다. 사방넷
  스케줄러와 같은 표다 — 줄마다 쇼핑몰 · 쇼핑몰 ID · 사용여부 · 설정 · 등록 상품과 되는 일 열 칸
  (주문수집 · 클레임수집 · 운송장 송신 · 문의수집 · 문의답변 · 상품등록 · 상품수정 · 품절관리 · 판매재개 ·
  재고송신). 칸은 켜고 끄는 스위치가 아니라 **그 일이 지금 되는지**다(`_shared/mall-capabilities.ts`).
  경로가 없는 일에 초록을 칠하지 않는다. 사방넷의 상품상태송신 한 칸은 품절관리 · 판매재개 둘로 가른다 —
  매니페스트의 `soldOutRoute` · `resumeRoute` 가 각 칸의 초록이고, 몰이 해제를 자동으로 받지 않으면
  판매재개만 빨강이다(사장님 2026-09-19).
- 몰에 올라간 상품은 사방넷 송신 기록에서 한꺼번에 가져온다(KID-246, `_shared/SabangnetListingsImport`).
  쇼핑몰 현황 머리와 등록 현황의 '안 가져온 몰' 안내에 같은 컨트롤이 선다. 가져오기가 끝나면
  그 화면이 가져온 몰 계정마다 매칭 owner 의 자동 매칭을 부른다 — 완료가 매칭을 대신 돌리지 않는다.
- 사방넷에 없는(또는 일부만 오는) 키드키즈 · 아이스크림몰 · 온채널 · 꼬망세 · 올웨이즈 · 아트공구는 그 몰 관리자에서 직접 가져온다(KID-246 2단계,
  `_shared/MallAdminListingsImport`, 몰마다 컨트롤 하나). 같은 두 화면에 사방넷 컨트롤과 나란히
  선다. 끝나면 그 몰 계정의 자동 매칭을 부른다. 몰을 늘리는 일은 확장 읽기기 하나와
  `@kiditem/shared/mall-admin-listings` 몰 표 한 줄이다.
- `/mall-listings`: 탭 두 개. **등록 현황**은 상품 마스터 × 몰 매트릭스이고,
  **새 등록**은 수집상품에서 출발하는 4단계 마법사다. 기준 엔티티가 다른 것은
  리스팅이 마스터에 걸려 있기 때문이고, 억지로 합치면 둘 중 하나가 빈 표가 된다.
  화면은 몰을 하나도 모른다. 몰을 아는 것은 어댑터뿐이다.
- `/mall-availability`: 일괄 품절·해제. 판정은 재고 도메인 것을 읽기만 한다. 품절은 같은 값으로
  되돌릴 수 있어 확장이 그 몰 관리자의 자기 버튼이 보내는 요청 그대로 끝까지 보낸다
  (`mall-availability-send`, 몰은 `MALL_AVAILABILITY_SEND_MALLS`). 보냈다는 것은 `attention` 이고,
  보낸 뒤 몰을 다시 읽어 전부 확인된 것(도매꾹 · 쿠팡 윙)만 `succeeded` 다(`availabilityOutcome`). 등록현황
  칸의 품절 · 판매 재개도 같은 판정을 쓴다. 도매꾹 품절은 진열안함이다. 꼬망세 품절은 노출/재고 설정 화면 줄마다의
  [개별수정]으로 재고 0(재개 999)만 바꾼다 — 페이지 전체를 다시 저장하지 않는다. 티쳐몰 품절은 [실물] 일괄 업데이트의
  재고 0(재개 999)이다 — 정보수정은 승인이 풀려 쓰지 않고, 보낸 뒤 "미승인"이면 알린다. 카카오 톡스토어 품절은 판매자센터
  [선택 수정]의 재고 0 이고(옵션 있는 상품은 보내지 않는다), 올웨이즈는 [품절] · [판매재개] 버튼과 같은 요청이다
  (토큰은 판매자센터 화면 안에서만 쓴다). 아트공구 품절은 카페24 상품목록의 [판매안함], 해제는 [판매함]이다
  (세트상품은 보내지 않는다). 롯데ON 품절은 판매자센터 상품정보일괄수정의 판매상태 품절(SOUT), 해제는 판매중(SALE)이고
  (롯데ON이 판매중지 · 판매종료한 상품은 보내지 않는다), 요청 머리는 판매자센터 화면 함수가 붙인다. 아이스크림몰 품절은
  상품 정보 관리 [판매상태 일괄변경] 창의 품절(20), 해제는 판매중(10)이다(판매종료 · 예약상품 품절은 보내지 않는다).
  키즈노트 품절은 판매 상품 내역 [상태/노출일괄수정]의 품절, 해제는 정상이다(숨김은 보내지 않는다 — 상품번호 검색이
  없어 목록을 100개씩 넘겨 찾는다). 지마켓 · 옥션(ESM) · 11번가 · 스마트스토어는 품절을 판매중지로 보낸다 — 그 몰
  관리자의 품절 길이 판매중지이고(ESM 은 재고 0 을 못 받는다), 칸도 '판매중지'라고 적는다. 몰 API 는 확인 전
  (`unverified`)이라 등록 · 수정은 닫혀 있고 품절 · 재개 축만 열린다. ESM 판매중지를 오래 두면 몰이 상품을 지운다
  (지마켓 13개월 · 옥션 90일). 떠리몰(샵바이)도 품절이 판매설정 판매중지 · 재개가 판매가능이다 — 판매금지는 되돌릴 수
  없어 보내지도 풀지도 않는다. 키드키즈는 상품코드로 검색한 그 줄의 목록 폼을 [일시품절] · [품절해제]처럼 EUC-KR 로
  숨은 창에 제출한다(목록은 수정일 동률이라 쪽을 넘겨선 못 찾는다). 품절 송신은 이미 못 사는 상태(판매종료 · 숨김 ·
  판매불가 등)를 "이미 된 것"으로 세고, 칸 알약과 창은 몰이 준 상태 글자를 그대로 적는다 — 품절 처리가 만드는
  품절 · 판매중지만 빨강이고, 몰이 막은 판매불가 · 판매금지 · 보류 · 반려는 주황, 등록대기 · 승인대기 · 사방넷 대기중은 "미승인",
  판매종료 · 숨김 · 미노출은 회색이다. 사방넷 · 몰 관리자에서 가져온 상태와 확장이 지금 읽은 상태가 한 표
  (`mallStopBadge` · `listingStatePill`)에서 말과 색을 받는다 — 못 사는 칸을 모두 "품절"로, 몰 관리자 품절을 "판매중지"로 접지 않는다. 칸 창의
  "몰에서 보기"는 서버가 확인한 몰만 만든 상품 페이지 주소다(`mall-product-url`, 쿠팡은 가져올 때 받은 productId).
  쿠팡 윙 품절은 옵션 재고 0 이다(윙에서
  품절과 판매중지는 다르다) — 옵션 단위라 품절 옵션만 바꾸고(`mallOptionCode`), 해제는 재고 0 인 옵션만 되살린다.
  확장은 윙 상품목록(`vendor-inventory/list`)에서 보낸다 — 칸에서 상품 하나를 누르면 그 상품을 검색한 상품목록을
  앞에 띄워 보내고, 상품목록이 늦게 따라오므로 바뀐 재고가 보일 때까지 새로 고친다(`show`, `listShown`). 일괄은 웹이 10개씩 나눠 보내며 진행을 보이고, 확장은 상품목록을 뒤에서
  열고 닫는다. 윙이 429 로 막아 멈추면 남은 상품은 보내지 않은 것으로 센다. 윙은 품절이어도 판매상태가
  ON_SALE 이라, 등록현황은 페이지가 뜨면 그 페이지의 쿠팡 칸을 윙에서 한 번에 읽어(`useMallLiveAvailability`,
  읽기만 · 저장 안 함 · 열린 윙 화면을 빌려 씀) 품절이면 칸을 빨간 '품절', 일부면 '일부 품절'로 보인다. 칸의 창도 같은
  값을 보이고, 품절 · 재개 뒤에는 닫지 않고 그 칸만 다시 읽는다(조회가 늦게 따라오는 롯데ON 은 확장이 몰에서 확인한
  상태를 그대로 둔다).
  상품 단위로 보내는 몰은 옵션 일부만 품절인 상품을 보내지 않는다 — 서버 미리보기
  (`previewAvailability`)가 막고 이유를 붙인다.
- `/mall-tasks`: 등록·품절 실행 기록을 한 표에서 상태로 본다.

`/mall-settings`(쇼핑몰 계정)는 `app/(orders)/` 에 남아 있다. 그 화면은 몰 계정 행
(`channel` = 몰 키, ADR-0012)의 로그인(`config.orderCollection`)을 편집하므로 Orders API 를
쓴다. 등록 쪽은 계정 행을 만들지 않는다 — 없으면 '계정 정보 필요'로 멈춘다. 사이드바에서 같은
섹션에 있다는 이유로 이 그룹으로 옮기지 말 것.

## 상태 규칙

- 몰별 제약(완전품절=삭제, 비가역 상태, 승인 개입, 전체 재전송, 호출 상한)은 서버
  `MallAdapterManifest` 가 유일한 권위다. 화면에 상수로 다시 적지 않는다.
- 성공은 몰 재조회로 확인된 것(`published`)뿐이다. 전송 완료(`submitted`)를 성공으로
  표시하지 않는다.
- 리스팅을 한 번도 가져오지 않은 몰의 빈 칸은 '몰에 없다'가 아니라 '우리가 모른다'다.
  열과 카드가 `imported` 로 그 차이를 말한다. 모르는 자리에 0 을 찍지 않는다.
- 몰 원문 상태는 도메인(`mall-listing-state.ts`)이 우리 어휘로 접는다. 접히지 않는
  값은 `unknown` 이고, 발행으로도 오류로도 추측하지 않는다. 특히 쿠팡 적재가
  심사중과 반려를 같은 `draft` 로 뭉개므로 그 값은 확인필요로 남긴다.
- 응답이 확인되지 않은 건은 성공에도 실패에도 넣지 않고 `unknown_needs_reconcile`
  로 노출한다.
- 품절 해제는 품절과 같은 명령이다. 별도 화면·별도 버튼 계열로 분기하지 않는다.
- 판매 가능 재고는 `ChannelSkuAvailability` 가 계산한다. 이 그룹에서 용량을 다시
  계산하지 않는다.

## 어댑터 규칙

몰에 보내는 경로는 `_shared/adapters/` 의 `MallPublishAdapter` 구현만 가진다.
몰을 늘리는 일은 그 파일 하나를 더하고 레지스트리에 등록하는 것이고, 화면·상태·
버튼을 몰마다 새로 만들지 않는다.

- 페이지와 컴포넌트는 확장도 몰 엔드포인트도 직접 부르지 않는다. 어댑터만 부른다.
- `kind: 'api'` 몰은 백엔드가 소유한다. 어댑터는 우리 API 를 부른다.
- `extension_form` / `extension_excel` 몰은 브라우저가 소유한다. 몰 관리자 세션이
  브라우저에만 있어 백엔드가 대신 열 수 없다 — 이건 설계 선택이 아니라 제약이다.
- 어댑터는 `ok`(보냈다)와 `confirmed`(등록됐다)를 따로 보고한다. 폼을 채운 것도
  엑셀을 만든 것도 `confirmed` 가 아니다.
- 어댑터는 자기 입력칸을 `fields` 로 선언한다. 화면이 몰별 입력 폼을 하드코딩하지
  않는다. 값의 출처(`master`/`template`/`override`)를 함께 선언해 사람이 무엇이
  상품에서 오고 무엇이 이 몰 고정값인지 보게 한다.
- 사람이 고르는 `override` 값은 **상품에 저장한다**(`manualBasics.mallRegisterValues`,
  공통 칸은 `mallRegisterShared`). 등록할 때마다 다시 받으면 같은 상품인데 몰마다 다른
  값이 들어간다. 등록 준비가 있어도 수집상품 후보에만 저장하고 준비 `registrationInput`
  에는 넣지 않는다 — 송신 전 점검과 폼 채우기가 후보 문서를 읽는다. 저장은 사람이 고친 값만 담는다 — 어댑터 기본값까지 저장하면 기본값을
  고쳐도 저장된 상품이 옛 값에 묶인다(`_shared/mall-register-values.ts`).
- "왜 이 몰에 못 보내는가" 는 `adapter.validate` 만이 답한다. 화면이 몰별 조건을 다시
  적으면 버튼은 열려 있는데 보내면 막히는(또는 그 반대의) 화면이 된다.
- 승인제 몰(`requiresOperatorApproval`)은 확장이 제출하지 않는다. 폼만 채우고
  사람이 누른다.

## 경계 규칙

- 이 그룹의 서버 호출은 `_shared/mall-publishing-api.ts` 를 통한다.
- 파괴적 동작(완전품절, 삭제)은 매니페스트가 허용한 경우에만 버튼이 활성화되고,
  강등된 경우 실제로 보낼 상태를 화면에 표시한다.
